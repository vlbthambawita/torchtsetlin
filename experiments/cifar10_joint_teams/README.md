# cifar10_joint_teams: batch size for jointly trained, augmented TM teams on CIFAR-10

**Question.** How does the mini-batch size change the accuracy and the training time of a *jointly
trained team* of convolutional Tsetlin machines on CIFAR-10, when every run trains with data
augmentation? Teams only: no single models, no independent composites, no un-augmented runs.
W&B mirror: https://forge.coreweave.com/wandb/simulamet_mlc/TM_CIFAR (runs `cjt-…`).

Builds on `../joint_wide_tm` (the joint update: members share one vote sum for feedback) and
`../cifar10_batch_clauses` (CIFAR-10 files, the 45 000 / 5 000 split, the runner scripts).

## Quick start (server with 4 GPUs, one GPU per tmux session)

```bash
git clone -b joint-wide-tm https://github.com/vlbthambawita/torchtsetlin.git
cd torchtsetlin/experiments/cifar10_joint_teams
wandb login --host https://api.forge.coreweave.com   # once (after setup.sh created .venv: . .venv/bin/activate)
./setup.sh          # once, in any session: environment, GPU check, data, checks, smoke test (~15 min)
./run_gpu0.sh       # tmux session 1
./run_gpu1.sh       # tmux session 2
./run_gpu2.sh       # tmux session 3
./run_gpu3.sh       # tmux session 4
./status.sh         # progress, cost table, chosen augmentation policy
```

A runner uses whichever single GPU its session sees; the number only names it (`logs/gpuK.log`).
All four must run in the same folder: they share one job list through `.cache/claims/`. Each
`run_gpuK.sh` starts a background runner (log `logs/gpuK.log`, one log per run in `logs/runs/`);
`CJT_FG=1 ./run_gpu0.sh` keeps it in the foreground of the tmux pane instead.

The runners work through **pricing** (9 short timings) → **augmentation pilot** (3 runs, picks the
policy) → **batch-size grid** (14 runs, longest first) and exit when nothing is left. Re-running a
script resumes: finished runs are skipped, interrupted runs continue from their checkpoint
(every 5 epochs). `./stop.sh` stops after the current runs, `./stop.sh --now` immediately; remove
`STOP` to continue.

Later phases, on request only:

```bash
CJT_PHASES=ext ./run_gpu0.sh                                   # team M at B = 1 and 4
CJT_PHASES=large CJT_LARGE_BATCHES=32,128,1024 ./run_gpu0.sh   # the five-member team L
CJT_PHASES=pricing ./run_gpu0.sh                               # only the cost table
```

Clause sweep (2026-11-18, after the batch grid): the best team (M) at batch 64 with larger
members, one run per GPU, largest first. Start one script per tmux session:

```bash
./run_clauses_gpu0.sh   # ... ./run_clauses_gpu3.sh
```

It first times 30 updates per size (`cprice`: s/epoch and peak memory in `./status.sh`), then runs
16 000, 32 000, 64 000 and 128 000 clauses per class and member (tags `M_b64_<policy>_s0_c<N>`,
phase `clauses`, checkpoint every epoch, time cap 120 h). T stays at the Toolbox value of each
member. Options (use the same in all sessions): `CJT_CLAUSES=16000,32000`, `CJT_CLAUSE_BATCH=32`,
`CJT_T_MODE=scaled` (T in proportion to the clauses, tag `..._Tscaled`), `CJT_TIME_CAP_H=72`,
`CJT_PHASES=cprice` (cost table only).

Results come back with `rsync -a <server>:<path>/results/ results/` and
`rsync -a <server>:<path>/figures/ figures/` (or a commit); then `python code/report.py`. The
best-epoch teams stay in `models/` on the server (git-ignored).

Knobs: `CJT_VENV=none` (use the active Python), `PYTHON=python3.12`, `TORCH_INDEX=<wheel index>`,
`CJT_WANDB=0` (no W&B), `CJT_WORKERS=<n>` (augmentation processes per runner, default
cores/4 − 1, at most 8), `CJT_SKIP_SMOKE=1`.

## Rules

| # | Rule |
|---|---|
| R1 | `src/torchtsetlin/**` is **read-only** here. Library defects go to `LIBRARY_GAPS.md`. |
| R2 | Every number comes from a `results/<phase>/<tag>.json` record carrying `argv`, `seed`, `git_sha`, `env`. W&B is a mirror. `REPORT.md` is generated by `code/report.py`; do not hand-edit. |
| R3 | Nothing is tuned per batch size. The only selection is the augmentation policy (pilot, on validation). |
| R4 | Early stopping watches the 5 000-image validation split, never the test set. Validation and test images are never augmented. |
| R5 | Seed 0 only until more seeds are approved. |

## Design

Members (2 000 clauses per class each, weighted, `max_included_literals=32` soft, position bits;
T and s from the Optimized Toolbox, arXiv:2406.00704, Table III):

| Id | Binarization | Convolution | Filter | T | s |
|---|---|---|---|---|---|
| H3 / H4 / H5 | colour thermometer, 8 levels (24 planes) | 2D | 3×3 / 4×4 / 5×5 | 3000 | 5 |
| G5 | adaptive Gaussian threshold (3 planes) | 2D | 5×5 | 2500 | 3.5 |
| M10 | adaptive mean threshold (3 planes) | 2D | 10×10 | 500 | 10 |
| B3 | 8 bit planes per colour (3 × 8) | 3D | 8×3×3 | 3000 | 5 |

| Team | Members | Batch sizes |
|---|---|---|
| **M** (mixed, primary) | H3 + M10 + B3 | 16, 32, 64, 128, 256, 512, 1024 (+ 1, 4 in `ext`) |
| **S** (filter shapes) | H3 + H4 + H5 | 16, 32, 64, 128, 256, 512, 1024 |
| **L** (large) | H3 + H5 + G5 + M10 + B3 | `CJT_LARGE_BATCHES` |

Joint rule `sum`: every member's feedback uses the team score Σ votes with threshold Σ T and one
shared negative class; prediction = argmax of the summed votes.

**Augmentation** (AlbumentationsX, on the uint8 image before binarization, training images only):

| Policy | Transforms |
|---|---|
| `geo` | shift ±4 px (reflect-pad 40 + random crop 32), horizontal flip |
| `geo+col` | `geo` + colour jitter (brightness, contrast, saturation 0.2; hue 0.02; p = 0.5) |
| `full` | `geo+col` + affine (scale 0.9–1.1, rotate ±10°, p = 0.5) + cutout (one 8×8 hole, p = 0.5) |

Each image is augmented once per epoch and then binarized for every member. Its random stream
depends only on (seed, epoch, image index), so **every batch size trains on exactly the same
augmented epochs**. Worker processes prepare the next epoch while the current one trains.
AlbumentationsX is AGPL-3.0 and is imported only by `code/augment.py`; its usage telemetry is
switched off (`env.sh`, `code/augment.py`). On Python < 3.11 `setup.sh` falls back to
`albumentations==2.0.8`; the record's `env.augmentation_lib` says which was used.

**Training:** early stopping on validation accuracy (patience 30, at least 60, at most 200 epochs,
48 h cap); pilot runs have a fixed 40 epochs. Statistic: test accuracy at the best-validation epoch.

**Explanations:** every 10 epochs (and at the last epoch) the activation-map panel of 20 fixed
validation images (two per class, `results/panel.json`) is written to
`figures/activation/<phase>/<tag>/eNNN.png` and logged to W&B as `viz/panel`: image, team evidence
map, one map per member, and the three strongest matching clauses. Maps are exact: a member's map
sums to its class vote, the member maps add up to the team score. For a saved team:
`python code/viz.py models/grid/<tag>.pt`.

## Layout

| Path | What |
|---|---|
| `setup.sh`, `env.sh` | one-time setup; shared environment (venv, W&B host, telemetry off) |
| `run_gpu0.sh` … `run_gpu3.sh`, `run_gpu.sh`, `gpu_device.sh` | one runner per GPU slot |
| `run_clauses_gpu0.sh` … `run_clauses_gpu3.sh`, `run_clauses_gpu.sh` | the same runners on the clause sweep |
| `status.sh`, `stop.sh` | progress; graceful / immediate stop |
| `code/common.py` | members, teams, grid, paths, data + split, records |
| `code/augment.py` | AlbumentationsX policies, per-image seeding, look-ahead worker pool |
| `code/encoders.py` | thermometer and bit planes (GPU); adaptive thresholds (OpenCV, in `augment.py`) |
| `code/team.py` | `JointConv3d`, building / saving / loading teams (joint update from `joint_wide_tm`) |
| `code/train.py` | one run (or `--calibrate N` for pricing) |
| `code/viz.py` | activation-map panel, during training and on a saved team |
| `code/tracking.py` | W&B mirror, id `cjt-<phase>-<tag>`, group `cjt-<team>` |
| `code/queue_runner.py` | shared job list, claims, pilot choice |
| `code/check_team.py`, `code/resume_check.py` | phase-0 checks |
| `code/report.py` | `REPORT.md`, `results/summary.json`; `--status` for progress |
| `models/<phase>/<tag>.pt` | **not in git**: the team at its best-validation epoch |
